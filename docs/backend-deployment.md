# Backend deployment

## Deployment objective

This repository remains a **Vite** frontend deployed on Vercel, with serverless API routes under `api/`. Deployment is considered correct only when the frontend build succeeds, the API routes receive the full environment contract, the Supabase schema is migrated in order, and Stripe is configured to send signed webhook events to the deployed backend.

## Step 1: provision external services

Provision a Stripe account, a Supabase project, and a Resend account before deployment. The backend expects all three services to be active because checkout, persistence, and transactional email are not optional subsystems.

| Service | What must exist before deploy |
| --- | --- |
| Stripe | Three one-time prices matching the canonical offers and a webhook endpoint secret |
| Supabase | A project URL and service-role key |
| Resend | An API key and a verified sender domain or sender address |

## Step 2: set environment variables in Vercel

Populate the exact keys from `.env.example` in the Vercel project settings.

| Variable | Deployment note |
| --- | --- |
| `APP_BASE_URL` | Use the canonical production origin, for example `https://runway-fuel-site.vercel.app` or the custom domain |
| `STRIPE_SECRET_KEY` | Use the live key in production and the test key in preview or staging |
| `STRIPE_WEBHOOK_SECRET` | Use the secret generated by the Stripe webhook endpoint |
| `VITE_STRIPE_PUBLISHABLE_KEY` | Required for frontend checkout wiring |
| `RUNWAY_FUEL_DIAGNOSTIC_PRICE_ID` | Must point to the Stripe price for `rf_diagnostic` |
| `RUNWAY_FUEL_BLUEPRINT_PRICE_ID` | Must point to the Stripe price for `rf_blueprint` |
| `RUNWAY_FUEL_DEPOSIT_PRICE_ID` | Must point to the Stripe price for `rf_deposit` |
| `SUPABASE_URL` | Project URL from Supabase |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-only key; never expose this in frontend code |
| `RESEND_API_KEY` | API key for transactional delivery |
| `RUNWAY_FUEL_FROM_EMAIL` | Verified sender, for example `Runway Fuel <ops@yourdomain.com>` |
| `RUNWAY_FUEL_NOTIFICATION_EMAIL` | Internal operations inbox |
| `ADMIN_API_TOKEN` | Long random secret used as a Bearer token for `/api/get-usage` |

## Step 3: apply Supabase migrations in order

Run the SQL migrations in the exact sequence below.

| Order | File | Purpose |
| --- | --- | --- |
| 1 | `supabase/001_runway_fuel_core.sql` | Creates tables, constraints, triggers, and indexes |
| 2 | `supabase/002_runway_fuel_policies.sql` | Enables row-level security and blocks direct client access |

These migrations are written for execution in the Supabase SQL editor or any equivalent migration runner. The backend assumes the schema already exists before the first real webhook arrives.

## Step 4: configure the Stripe webhook endpoint

In Stripe, create a webhook endpoint that points to the deployed route:

```text
https://YOUR_DOMAIN/api/stripe-webhook
```

Subscribe at minimum to the `checkout.session.completed` event. Copy the signing secret generated by Stripe and store it as `STRIPE_WEBHOOK_SECRET` in Vercel.

The webhook route verifies the raw request body signature. If the signature is invalid, the request is rejected. If Stripe retries the same completed session, the backend treats the request idempotently and will not create a duplicate order.

## Step 5: deploy on Vercel

This project should stay configured as a Vite deployment.

| Setting | Value |
| --- | --- |
| Framework preset | `Vite` |
| Install command | `pnpm install` |
| Build command | `pnpm build` |
| Output directory | `dist` |
| Root directory | `./` |

The `vercel.json` file in the repository preserves these assumptions.

## Step 6: validate the deployment

Run the local validation sequence before pushing, and repeat the functional checks after deployment.

### Local validation

```bash
pnpm install
pnpm build
node --check api/_lib/env.js
node --check api/_lib/http.js
node --check api/_lib/offers.js
node --check api/_lib/stripe.js
node --check api/_lib/supabase.js
node --check api/_lib/email.js
node --check api/_lib/logging.js
node --check api/create-checkout-session.js
node --check api/stripe-webhook.js
node --check api/submit-intake.js
node --check api/get-order.js
node --check api/get-usage.js
```

### Post-deploy validation

| Check | Expected result |
| --- | --- |
| `POST /api/create-checkout-session` with a canonical offer and email | Returns `checkoutUrl` and `sessionId` |
| Stripe test checkout completion | Creates exactly one order in `rf_orders` |
| Webhook replay | Returns success without creating a second order |
| `POST /api/submit-intake` for the paid order | Stores intake and moves status to `intake_received` |
| `GET /api/get-order` for that order | Returns the correct order summary |
| `GET /api/get-usage` with Bearer token | Returns revenue and status summaries |

## Step 7: operational hardening

Once deployment is live, keep the service-role key and admin token restricted to Vercel server-side configuration only. Do not reuse the admin token in browser code. Do not trust any client-supplied price or amount, even for internal tools.
